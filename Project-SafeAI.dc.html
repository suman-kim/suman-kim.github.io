SafeAI 산업안전

카메라 옆 AI 보드가 현장의 위험을 감지하면, 관제 콘솔에서 실시간 영상으로 확인하고 PTT 무전으로 바로 지시하는 산업안전 관리 플랫폼입니다. 서버와 콘솔, 영상·음성 구조, 엣지 보드 연동부터 배포·모니터링 인프라까지 플랫폼 전반을 개발했고, 한국전력공사에 납품했습니다.

01 · Background

배경 / 문제 정의

위쪽 대시보드는 납품 화면을 공개할 수 없어 실제 구성을 바탕으로 다시 그린 예시 화면입니다.

문제

산업 현장의 사고는 몇 초 사이에 일어나지만, 관제 인력이 수십 대의 CCTV를 계속 지켜보는 방식으로는 그 순간을 잡기 어렵습니다. SafeAI는 AI 보드가 영상에서 위험을 먼저 감지하고, 관제자가 감지된 장면을 바로 확인한 뒤 현장 작업자에게 무전으로 지시하는 흐름을 하나의 플랫폼으로 묶었습니다.

요구사항

원청과 여러 협력사가 한 플랫폼을 함께 쓰기 때문에 회사 간 데이터가 절대 섞이면 안 됐고, 같은 코드가 클라우드 SaaS와 인터넷이 끊긴 폐쇄망 현장 양쪽에 설치되어야 했습니다. 현장 방화벽에 인바운드 포트를 열 수 없다는 제약도 있었습니다.

서버가 당겨오는 RTSP

보드가 먼저 맺은 WireGuard 터널 안에서 MediaMTX가 카메라 RTSP 주소로 직접 접속합니다. 현장 쪽에 포트를 열지 않아도 영상이 들어옵니다.

이벤트 → 녹화 구간 재생

AI 보드가 감지한 이벤트의 프레임 이미지는 MinIO에 저장하고, 재생을 누르면 이벤트 시각 ±10분의 녹화 세그먼트를 찾아 그 장면부터 보여 줍니다.

작업자 단말 영상

Android 앱이 SRT로 보낸 단말 카메라 영상도 같은 MediaMTX 경로로 받아, CCTV와 같은 화면 · 같은 녹화 정책으로 관제합니다.

RECORDING POLICY

상시 녹화디스크가 차지 않는 녹화 보존 정책

모든 카메라와 단말 스트림을 24시간 녹화하면 디스크는 언젠가 반드시 찹니다. 특히 폐쇄망 현장은 누군가 들어가서 지워 줄 수 없기 때문에, 보존 기간과 디스크 보호를 서버가 스스로 지키도록 만들었습니다.

세 겹의 보호

  1. 녹화는 fMP4 10분 세그먼트로 쌓고, 7일(168h)이 지나면 MediaMTX가 자동 삭제
  2. 10분마다 100KB 미만의 빈 세그먼트를 정리
  3. 디스크 사용률이 80%를 넘으면 가장 오래된 파일부터 200개씩, 80% 밑으로 내려갈 때까지 삭제
보존 설정이 실수로 빠지지 않도록 CI 정적 검사에서 녹화 만료 설정과 정리 스크립트 존재 여부를 매번 확인합니다.

PERMISSION

권한 설계듣기와 말하기를 분리한 무전 권한

관제가 목적인 관리자는 회사의 진행 중 작업 무전을 모두 들을 수 있어야 하지만, 아무나 채널에 끼어들어 말하면 현장 지시가 엉킵니다. 그래서 듣기와 말하기를 서로 다른 계층에서 판단하도록 나눴습니다.

  • 듣기 — 채널 목록 API와 PostgreSQL RLS가 회사 범위를 강제. 관리자는 진행 중 작업 전체, 작업자는 자기 작업만
  • 말하기 — 발언권 서버가 채널 멤버인지 직접 검사. 멤버는 작업계획서의 작업자 명단에서 오고, 관제자는 dispatcher로 추가
  • 거절된 발언 요청은 그 시점의 멤버 목록과 함께 감사 로그로 남겨, 왜 말할 수 없었는지 바로 확인

SOFTWARE DELIVERY

태흥 소프트웨어 관리 플랫폼어느 현장에 어떤 버전이 깔려 있는지

제품은 클라우드에도, 고객사 현장 서버에도 설치됩니다. 현장 설치형으로 나가는 서버에는 경량 에이전트를 함께 심어 두고, 클라우드와 현장 모두 미리 설계해 둔 같은 프로토콜로 관리 플랫폼과 통신하게 했습니다.

  1. 에이전트가 첫 설치 시 OTP 인증번호를 발급받아 화면에 표시
  2. 관리자가 관리 플랫폼 페이지에서 그 번호를 입력하면 해당 PC와 매칭되고, 그때 에이전트 토큰이 발급
  3. 이후 에이전트가 설치된 제품 · 버전 · 컨테이너 상태 · 자원 정보를 주기적으로 보고
  4. 플랫폼은 응답으로 안내할 버전만 내려주고, 업데이트 실행은 제품의 설치기가, 실행 시점은 현장 관리자가 결정
플랫폼이 현장으로 먼저 요청을 보내는 일은 없습니다. 요청은 항상 에이전트에서 나가는 방향이라, 인바운드를 열 수 없는 현장 서버도 같은 방식으로 관리됩니다.

PROBLEM 01

PTT 음성 인식짧은 무전의 STT가 빈 텍스트로 나오던 문제

무전을 녹음해 Whisper로 텍스트를 남기는데, 짧은 무전일수록 결과가 비어 있었습니다. 원인은 순서였습니다. mediasoup consumer를 바로 재생 상태로 만들면, 녹음용 ffmpeg 프로세스가 뜨기 전에 RTP 패킷이 먼저 흘러가 버려 발언의 앞부분이 통째로 사라졌습니다.

해결

  1. consumer를 일시정지(paused) 상태로 만들고, ffmpeg가 수신 준비를 마친 뒤에 재개
  2. 준비 신호를 놓치는 경우를 대비해 800ms 뒤 한 번만 재개하는 폴백 추가
  3. 두 규칙을 CI 정적 검사의 불변식으로 등록해, 누가 고쳐도 되돌아가지 않게 고정
발언 1건 처리 순서개선 후
+0ms발언권 획득 · producer 생성
+4msconsumer 생성 paused
+180msffmpeg 수신 준비 완료
+181msconsumer resume · RTP 수신 시작
+3.2s발언 종료 · Whisper STT 요청
+4.1s"밸브 차단 확인했습니다" 기록

PROBLEM 02

배포 신뢰성"성공"으로 끝났는데 운영은 그대로였던 배포

예전 배포는 운영 서버가 개발 서버의 작업 디렉터리를 그대로 빌드하는 방식이라, 커밋되지 않은 파일이 운영에 올라가도 어떤 코드인지 답할 수 없었습니다. 원격 마이그레이션은 heredoc으로 넘겼는데, 안쪽의 docker exec -i가 표준 입력을 먹어 버려 마이그레이션 두 건이 복사만 된 채 "성공"으로 끝난 일도 있었습니다.

해결

  • 태그 커밋만 체크아웃해 CI 러너에서 빌드하고, 이미지를 운영으로 이식
  • 마이그레이션은 파일로 전송해 체크섬을 대조한 뒤 오류 시 즉시 중단 옵션으로 적용하고 원장에 기록
  • 같은 태그 재배포와 버전 역행을 차단하고, 배포 전 헬스 확인과 DB 백업
  • 배포 후 헬스 엔드포인트 200과 최근 60초 ORM 오류 0건을 확인, 실패하면 이전 이미지로 자동 롤백
클라우드 배포태그 푸시로 실행
사전 점검api · ptt · db healthy · 버전 역행 없음통과
백업DB 덤프 · compose · 현재 이미지완료

PROBLEM 03

컨테이너 네트워크가끔씩만 나는 connection refused

본 스택과 PTT 스택은 서로 다른 Compose 파일이지만 같은 Docker 네트워크를 공유합니다. 두 스택의 서비스 이름이 같은 DNS 이름으로 등록되자, nginx가 API로 보낸 요청 일부가 PTT 컨테이너로 가서 간헐적으로 connection refused가 났습니다. 로그만 보면 대부분 정상이라 원인을 찾기 어려운 종류의 장애였습니다.

해결

  • PTT 서비스 이름을 ptt-api로 고정해 DNS 이름 충돌을 제거
  • nginx upstream은 서비스 이름 대신 고유한 컨테이너 이름으로 지정
  • 예전 이름이 다시 들어오면 CI가 실패하도록 정적 검사 추가
한 번 겪은 장애는 CI의 불변식으로 남겨, 같은 문제가 조용히 돌아오지 않게 하는 방식으로 운영했습니다.
