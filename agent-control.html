결과차단 · 이 세션에 진행 중인 task가 없어서 파일 수정과 Bash를 막았습니다. task를 진행 중으로 바꾸면 풀립니다.

위 창은 직접 눌러 볼 수 있습니다. task를 연결하지 않고 보내면 막히고, 연결한 뒤 보내면 이 페이지 테마가 실제로 바뀝니다.

만든 이유

앱 세 개LK · CM · HR를 번갈아 개발하다 보니, taskLK-57가 어디까지 갔는지와 어제 세션$ claude에서 한 일을 매번 다시 찾고 있었습니다.

불편했던 점

  • task가 저장소마다 따로 있었습니다

    처음엔 저장소마다 Task Master 파일로 task를 관리했습니다. Link 하나에만 270개가 쌓이고 나니, 다른 앱까지 합친 전체 상황은 볼 방법이 없었습니다.

  • 세션이 매번 처음부터 시작했습니다

    새 세션을 열면 어디까지 했는지부터 다시 설명해야 했습니다. 지난 세션에서 지적한 실수를 다음 세션이 그대로 반복한 적도 여러 번 있었습니다.

  • 적어 둔 규칙이 가끔 무시됐습니다

    CLAUDE.md에 “task부터 갱신할 것”, “main에 직접 push하지 말 것”을 적어 뒀지만, 규칙 파일은 참고 사항이라 지켜지지 않을 때가 있었습니다.

  • 확인할 곳이 너무 많았습니다

    어느 세션이 제 답을 기다리는지는 터미널을 하나씩 열어 봐야 알았고, PR은 GitHub, 배포는 Railway에서 따로 확인했습니다. 실행 비용은 볼 방법이 없었습니다.

만들면서 정한 것

  • task는 한 곳에서 관리

    task, 기획, 실수 기록, 실행 결과, 배포 기록을 전부 DB 하나에 모았습니다. 저장소에 있던 Task Master 파일은 한 번 가져온 뒤로 쓰지 않습니다.

  • 중요한 규칙은 코드로 막기

    꼭 지켜야 하는 건 hook에서 막도록 했습니다. 연결된 task가 없으면 파일을 고칠 수 없고, push는 에이전트 대신 서버가 합니다.

  • 저는 확인하고 결정하는 일만

    실행하고 기록하는 건 서버에 맡기고, 저는 기획을 승인하거나 질문에 답하고 PR을 머지하는 일만 합니다.

task 하나가 PR이 되는 과정

실행을 누르면 작업용 브랜치를 따로 만듭니다.

대시보드에서 실행하면 큐에 들어갔다가, 차례가 오면 git worktree로 작업 폴더를 따로 만듭니다. 원래 저장소에는 손대지 않습니다.

에이전트가 작업하는 동안 로그가 계속 올라옵니다.

허용한 도구만 쓸 수 있고 push 권한은 없습니다. 출력은 줄 단위로 DB에 저장되고, 대시보드에서 실시간으로 볼 수 있습니다.

중간에 질문이 오면 답하고 이어서 진행합니다.

질문으로 끝나면 task가 ‘답변 대기’로 바뀝니다. 답을 보내면 같은 세션을 이어서 실행하기 때문에 앞의 대화가 그대로 남아 있습니다.

검사를 통과하면 서버가 PR을 올립니다.

push 전에 앱마다 정해 둔 검사 명령을 돌리고, 실패하면 PR을 만들지 않습니다. 제가 머지하면 task가 완료되고 작업 폴더도 지워집니다.

주요 기능

오른쪽 화면은 실제 대시보드와 세션 화면을 같은 구성으로 옮겨 그린 것입니다. 시연 영상은 준비되는 대로 붙이고 있습니다.

세션 시작 시 맥락 전달

새 세션이 열리면 hook이 지금 앱의 task 상황과 지난 실수 기록을 모아서 세션에 넣어 줍니다. 덕분에 어디까지 했는지 설명할 일이 거의 없어졌습니다.

  • 넣는 순서는 앱 정보, 이 세션의 task, 열린 task, 실수 기록 순이고 8,000자를 넘으면 뒤에서부터 자릅니다.
  • 세션은 MCP 도구로 task 상태를 바꾸고, 실수나 인수인계 문서, 버그를 직접 기록합니다.
  • 인수인계 문서는 저장소의 docs/ 폴더에도 복사돼서 다음 세션이 읽을 수 있습니다.
  • 작업 규칙은 대시보드에서 수정하면 모든 세션의 규칙 파일에 반영됩니다.

task 없는 수정 차단

규칙 파일에 적어 두는 것만으로는 부족해서, 파일 수정이나 Bash를 실행하기 직전에 서버가 허용 여부를 판정하도록 만들었습니다.

  • 진행 중인 task가 연결되지 않은 세션은 수정과 Bash가 막힙니다. 읽기는 막지 않습니다.
  • 세션이 task를 ‘진행 중’으로 바꾸면 자동으로 연결되고, ‘리뷰’로 넘기면 다시 잠깁니다.
  • 등록하지 않은 프로젝트 폴더에서도 막힙니다.
  • 서버가 꺼져 있을 때는 막지 않습니다. 서버 문제 때문에 작업 전체가 멈추는 건 피하고 싶었습니다.

task 자동 실행과 PR 생성

task를 실행하면 따로 만든 작업 폴더에서 에이전트가 작업하고, 검사를 통과한 결과만 PR로 올라옵니다.

  • task마다 git worktree와 브랜치를 새로 만들어서 다른 작업과 섞이지 않습니다.
  • 에이전트에게는 push 권한이 없습니다. 검사가 통과하면 서버가 push하고 PR을 만듭니다.
  • 에이전트가 질문하면 멈춰서 기다리고, 답하면 같은 세션으로 이어서 실행합니다.
  • 실행마다 비용이 기록되고, PR이 머지되면 task가 자동으로 완료 처리됩니다.

세션 모니터링

터미널에서 직접 연 세션, 백그라운드 세션, 서버가 띄운 실행을 한 목록에서 봅니다. 세션이 여러 개 떠 있을 때 어느 쪽이 제 답을 기다리는지 터미널을 뒤질 필요가 없어졌습니다.

  • 상태는 hook 기록으로 추정합니다. 작업 중, 입력 대기, 30분 넘게 소식 없음, 종료 네 가지입니다.
  • 세션마다 연결된 task, 누가 시작했는지, 마지막 메시지와 도구를 보여 줍니다.
  • 세션을 누르면 대화 내용을 채팅 화면으로 볼 수 있습니다.
  • 백그라운드 세션은 원격 조종 링크로 바로 이어서 볼 수 있습니다.

앱별 상태와 배포 관리

앱마다 개발 단계, 배포 기록, 버그, 제가 직접 해야 할 일, 작업 히스토리, 비용을 한 페이지에 모았습니다.

  • 사이드바의 앱 이름 옆 점 색으로 가장 급한 상태를 보여 줍니다. 배포가 실패했거나 심각한 버그가 있으면 빨강, 답변 대기면 주황 식입니다.
  • GitHub 배포 기록과 Actions 결과를 5분마다 가져옵니다. 처음 연동했을 때는 90건을 가져오는 데 48초가 걸렸습니다.
  • 개발 중으로 둔 앱이 14일 넘게 조용하면 계속할지 멈출지 물어봅니다. 하루알바는 97일째라 이 알림이 떠 있습니다.
  • 스토어 제출처럼 제가 직접 해야 하는 일은 세션이 ‘내 할 일’로 따로 등록합니다.

기획 제안과 승인

앱마다 다음에 만들 만한 기능을 에이전트가 기획해서 올리고, 저는 승인하거나 수정 요청, 반려만 합니다.

  • 앱 방향성 메모, 열린 task, 이전에 반려한 이유를 참고해서 기획을 씁니다.
  • 기획 단계의 에이전트는 코드를 읽기만 할 수 있습니다.
  • 승인하면 예상 task와 기획 명세가 바로 만들어지고, 수정 요청을 보내면 새 버전이 올라옵니다.
  • 앱별로 주기를 정해 자동으로 돌릴 수 있는데, 구독 사용량이 80%를 넘으면 그 회차는 건너뜁니다.

새 앱 시작 자동화

아직 저장소도 없는 앱 아이디어를 기획으로 받아 보고, 승인하면 저장소 생성부터 첫 PR까지 자동으로 진행됩니다.

  • 지금 쓰는 스택을 참고하고, 비슷한 서비스와 시장을 웹에서 조사해서 기획을 씁니다.
  • 승인하면 폴더 생성, 첫 커밋, GitHub 비공개 저장소 생성까지 진행됩니다.
  • 그다음 백그라운드 세션이 기획을 읽고 UI 시안, 첫 task 구현, PR 순서로 작업합니다.
  • 중간에 실패하면 이미 끝난 단계는 건너뛰고 실패한 단계부터 다시 시작합니다.

운영

개발 도구이긴 하지만 매일 켜 두고 쓰기 때문에, 꺼지거나 데이터가 날아가지 않게 하는 데 신경을 썼습니다. 로그인하면 launchd가 서버를 띄우고 죽으면 다시 띄웁니다. DB가 Docker 안에 있어서 DB 포트가 열릴 때까지 기다렸다가 시작하고, 실행 중에는 맥북이 잠들지 않게 막아 둡니다.
