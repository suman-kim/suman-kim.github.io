01 · Why

만든 이유

앱 여러 개를 번갈아 개발하다 보니, task가 어디까지 갔는지와 어제 세션에서 한 일을 매번 다시 찾고 있었습니다.

불편했던 점

01task가 저장소마다 따로 있었습니다

처음엔 저장소마다 Task Master 파일로 task를 관리했습니다. Link 하나에만 270 개가 쌓이고 나니, 다른 앱까지 합친 전체 상황은 볼 방법이 없었습니다.

02세션이 매번 처음부터 시작했습니다

새 세션을 열면 어디까지 했는지부터 다시 설명해야 했습니다. 지난 세션에서 지적한 실수를 다음 세션이 그대로 반복한 적도 여러 번 있었습니다.

03적어 둔 규칙이 가끔 무시됐습니다

CLAUDE.md에 “task부터 갱신할 것”, “main에 직접 push하지 말 것”을 적어 뒀지만, 규칙 파일은 참고 사항이라 지켜지지 않을 때가 있었습니다.

04확인할 곳이 너무 많았습니다

어느 세션이 제 답을 기다리는지는 터미널을 하나씩 열어 봐야 알았고, PR은 GitHub, 배포는 Railway에서 따로 확인했습니다. 실행 비용은 볼 방법이 없었습니다.

만들면서 정한 것

01task는 한 곳에서 관리

task, 기획, 실수 기록, 실행 결과, 배포 기록을 전부 DB 하나에 모았습니다. 저장소에 있던 Task Master 파일은 한 번 가져온 뒤로 쓰지 않습니다.

02중요한 규칙은 코드로 막기

꼭 지켜야 하는 건 hook에서 막도록 했습니다. 연결된 task가 없으면 파일을 고칠 수 없고, push는 에이전트 대신 서버가 합니다.

03저는 확인하고 결정하는 일만

실행하고 기록하는 건 서버에 맡기고, 저는 기획을 승인하거나 질문에 답하고 PR을 머지하는 일만 합니다.

02 · Process

task 하나가 PR이 되는 과정

1
실행을 누르면 작업용 브랜치를 따로 만듭니다.

대시보드에서 실행하면 큐에 들어갔다가, 차례가 오면 git worktree로 작업 폴더를 따로 만듭니다. 원래 저장소에는 손대지 않습니다.

2
에이전트가 작업하는 동안 로그가 계속 올라옵니다.

허용한 도구만 쓸 수 있고 push 권한은 없습니다. 출력은 줄 단위로 DB에 저장되고, 대시보드에서 실시간으로 볼 수 있습니다.

3
중간에 질문이 오면 답하고 이어서 진행합니다.

질문으로 끝나면 task가 ‘답변 대기’로 바뀝니다. 답을 보내면 같은 세션을 이어서 실행하기 때문에 앞의 대화가 그대로 남아 있습니다.

4
검사를 통과하면 서버가 PR을 올립니다.

push 전에 앱마다 정해 둔 검사 명령을 돌리고, 실패하면 PR을 만들지 않습니다. 제가 머지하면 task가 완료되고 작업 폴더도 지워집니다.

세션이 시작될 때

  1. Claude 세션세션 시작

    터미널에서 연 세션이든 백그라운드 세션이든 똑같이 처리됩니다.

  2. hook세션 정보 전달

    작업 폴더와 세션 ID를 관제 서버로 보냅니다.

  3. 관제 서버앱 판별과 task 연결

    작업 폴더로 앱을 찾고, 이 세션에 연결된 task를 확인합니다.

  4. 관제 서버맥락 블록 조립

    앱, 이 세션의 task, 열린 task, 실수 기록 순서로 8,000자 안에 담습니다.

  5. Claude 세션맥락을 받은 채로 시작

    하던 task와 지난 실수 기록을 알고 대화를 시작합니다.

코드를 고치기 직전

  1. Claude 세션수정이나 셸 실행 시도

    파일 수정과 Bash만 검사합니다. 읽기는 늘 허용합니다.

  2. hook실행 전 확인

    도구를 실행하기 전에 관제 서버에 통과 여부를 묻습니다.

  3. 관제 서버가드 판정
    통과
    • 진행 중 task가 연결된 세션
    • 시스템이 띄운 세션
    • 관제 서버가 꺼져 있을 때
    차단
    • 진행 중 task 없음
    • 등록되지 않은 프로젝트 폴더
    • 이유와 푸는 법을 세션에 안내

도구를 쓴 직후

  1. hook사용 기록 전달

    명령과 도구 사용이 자동으로 쌓입니다. 토큰과 키는 가려서 저장합니다.

  2. 관제 서버task 상태를 바꿨나?

    응답이 아니라 DB의 실제 상태로 판단해, 거부된 변경은 무시합니다.

    진행 중, 답변 대기

    • 수정이 풀림
    리뷰, 완료

  1. 사람task 실행

    대시보드에서 실행을 누르거나 API를 한 번 부릅니다.

  2. 관제 서버대기열에 등록

    pg-boss 큐가 동시에 2개까지 꺼냅니다. 맥북 CPU와 디스크를 지키기 위한 제한입니다.

  3. runner격리된 작업 공간

    git worktree와 전용 브랜치를 만들고, 앱별 준비 명령을 실행합니다.

  4. runnerClaude 실행

    task 설명, 기획 명세, 완료 조건을 담아 실행합니다. 허용한 도구만 쓰고 push 권한은 없습니다.

  5. 관제 서버로그 저장과 실시간 전송

    출력 이벤트를 DB에 남기고 대시보드로 보냅니다. 원본도 그대로 보관합니다.

  1. 관제 서버결과 판정

    에이전트의 마지막 구조화된 출력으로 어떻게 끝났는지 가립니다.

  2. 사람PR 리뷰와 머지

    머지는 언제나 사람이 합니다.

  3. GitHub머지 감지

    5분마다 GitHub를 확인해 머지된 PR을 찾습니다.

  4. 관제 서버완료와 정리

    task를 완료로 바꾸고 worktree를 지웁니다. 실행 비용은 앱별, 월별로 합산됩니다.

  1. 관제 서버기획 생성 시작

    앱별 주기에 맞춰 자동으로, 또는 즉시. 구독 사용량이 80%를 넘으면 건너뜁니다.

  2. runner읽기 전용 에이전트가 기획 작성

    방향성 메모, 열린 task, 이전 반려 사유를 읽고 정해진 형식으로 냅니다. 새 앱 기획은 비슷한 서비스와 시장도 웹에서 조사합니다.

  3. 사람검토

  2. GitHub비공개 저장소 생성

    같은 이름이 있으면 덮어쓰지 않고 멈춥니다.

  3. 관제 서버작업 폴더 신뢰 등록

  4. Claude 세션백그라운드 세션 시작

    기획 읽기, UI 시안, 첫 task 구현, PR 순서로 진행합니다. 원격으로 이어 볼 수 있습니다.

  5. 관제 서버실패하면 이어서

    끝난 단계는 건너뛰고 실패한 단계부터 다시 합니다.

04 · Features

주요 기능

세션 시작 시 맥락 전달

새 세션이 열리면 hook이 지금 앱의 task 상황과 지난 실수 기록을 모아서 세션에 넣어 줍니다.

  • 넣는 순서는 앱 정보, 이 세션의 task, 열린 task, 실수 기록 순이고 8,000자를 넘으면 뒤에서부터 자릅니다.
  • 세션은 MCP 도구로 task 상태를 바꾸고, 실수나 인수인계 문서, 버그를 직접 기록합니다.
  • 인수인계 문서는 저장소의 docs/ 폴더에도 복사돼서 다음 세션이 읽을 수 있습니다.
  • 작업 규칙은 대시보드에서 수정하면 모든 세션의 규칙 파일에 반영됩니다.

task 없는 수정 차단

규칙 파일에 적어 두는 것만으로는 부족해서, 파일 수정이나 Bash를 실행하기 직전에 서버가 허용 여부를 판정하도록 만들었습니다.

  • 진행 중인 task가 연결되지 않은 세션은 수정과 Bash가 막힙니다. 읽기는 막지 않습니다.
  • 세션이 task를 ‘진행 중’으로 바꾸면 자동으로 연결되고, ‘리뷰’로 넘기면 다시 잠깁니다.
  • 등록하지 않은 프로젝트 폴더에서도 막힙니다.
  • 서버가 꺼져 있을 때는 막지 않습니다. 서버 문제 때문에 작업 전체가 멈추는 건 피하고 싶었습니다.

task 자동 실행과 PR 생성

task를 실행하면 따로 만든 작업 폴더에서 에이전트가 작업하고, 검사를 통과한 결과만 PR로 올라옵니다.

  • task마다 git worktree와 브랜치를 새로 만들어서 다른 작업과 섞이지 않습니다.
  • 에이전트에게는 push 권한이 없습니다. 검사가 통과하면 서버가 push하고 PR을 만듭니다.
  • 에이전트가 질문하면 멈춰서 기다리고, 답하면 같은 세션으로 이어서 실행합니다.
