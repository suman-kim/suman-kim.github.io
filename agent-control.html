01 / 왜 만들었나

문제는 도구가 아니라 관리였습니다

앱이 늘어나자 세션마다 하던 일을 다시 설명해야 했고, 한 번 지적한 실수를 다른 세션이 반복했습니다. 누가 어디까지 했는지, 비용은 얼마인지도 알 수 없었고, 에이전트가 task 없이 코드를 고치거나 main에 바로 반영하는 일도 생겼습니다. 그래서 목표를 하나로 정했습니다. 모든 AI 세션은 맥락을 받아 시작하고, 모든 작업은 task에서 시작해 PR로 끝난다.

  1. 01task작업은 항상 task에서 시작
  2. 02맥락 주입진행 task와 과거 실수를 세션에 전달
  3. 03격리 실행worktree에서 허용된 도구로만 작업
  4. 04검사판정과 사전 검사를 통과해야 다음 단계
  5. 05PRpush와 PR은 시스템이, 머지는 사람이
02 / 기능

기능과 시연

각 기능이 어떤 문제를 풀었는지와 실제로 동작하는 모습을 함께 담았습니다.

맥락 주입task 가드task → PR 기획 승인새 앱 시작대시보드규칙 관리
F1

세션 맥락 주입과 실수 학습

세션을 열 때마다 하던 설명을 시스템이 대신합니다. 지적받은 실수는 다음 세션부터 바로 반영됩니다.

  • 세션이 시작되면 hook이 현재 앱, 이 세션의 task, 열린 task, 이 앱의 실수 기록을 맥락 블록으로 주입
  • 세션은 MCP 도구로 task 상태 변경, 실수 기록, 기획 명세·인수인계 문서 저장, 버그 등록을 직접 수행
  • 명령과 도구 사용, 종료가 자동으로 기록되고 비밀값은 가려서 저장
  • 맥락 블록은 8,000자 상한 안에서 우선순위대로 구성
새 세션에 맥락 블록이 들어가는 모습
F2

task 강제 가드

규칙 문서에 적어 두는 것만으로는 지켜지지 않아서, task 없이는 코드를 고칠 수 없게 시스템으로 막았습니다.

  • 직접 연 세션은 진행 중 task가 연결되기 전까지 파일 수정과 셸 실행을 차단, 읽기는 허용
  • 세션이 task를 doing으로 바꾸는 순간을 감지해 세션과 task를 자동 연결, review로 넘기면 해제
  • 등록되지 않은 프로젝트 폴더도 차단해 관리 밖의 작업을 방지
  • 관제 시스템이 꺼져 있으면 가드도 열어, 관리 도구 때문에 개발이 멈추지 않도록 설계
task 없이 수정 시도 → 차단 → task 연결 후 진행
F3

task 하나로 PR까지 자동 실행

task를 실행하면 격리된 작업 공간에서 에이전트가 일하고, 검사를 통과한 결과만 PR로 올라옵니다.

  • task마다 git worktree와 전용 브랜치를 만들어 원본 저장소와 격리
  • 에이전트 실행 로그를 WebSocket으로 대시보드에 실시간 전송
  • 에이전트에게 push 권한을 주지 않고, 사전 검사를 통과하면 시스템이 직접 push하고 PR 생성
  • 에이전트가 질문으로 끝나면 대기, 답하면 같은 세션으로 이어서 실행
  • 동시 실행 수와 허용 도구를 설정으로 제한, PR이 머지되면 task 자동 완료
실행 → 실시간 로그 → 질문에 답변 → PR 생성
F4

기획 생성과 승인

앱마다 다음에 할 일을 제안받고, 사람은 승인·수정·반려만 결정합니다.

  • 앱의 방향성 메모, 열린 task, 최근 기획과 반려 사유를 입력으로 기획을 생성
  • 기획 단계의 에이전트는 읽기 도구만 사용
  • 승인하면 예상 task와 기획 명세가 자동으로 만들어지고, 수정 요청은 새 버전으로 이어짐
  • 앱별 주기를 정해 자동 생성할 수 있고, 사용량이 높으면 건너뜀
기획 생성 → 검토 → 승인 → task 생성
F5

새 앱 기획에서 첫 PR까지

저장소도 없는 새 앱을 구상하고, 승인하면 프로젝트 시작부터 첫 구현까지 이어집니다.

  • 기존 앱의 스택을 참고하고 비슷한 서비스와 시장을 웹에서 조사해 새 앱 기획을 제안
  • 승인하면 폴더 생성과 초기 문서 커밋, GitHub private 저장소 생성
  • 백그라운드 Claude 세션이 기획을 읽고 첫 task를 구현해 PR까지 진행
  • 중간에 실패하면 끝난 단계는 건너뛰고 이어서 재시도
새 앱 기획 승인 → 저장소 생성 → 첫 PR
F6

통합 대시보드

여러 앱의 상태와 할 일, 배포, 히스토리를 한 화면에서 봅니다.

  • 앱마다 진행 상태를 색으로 표시하고, 개발 단계(기획 → 설계 → 개발 → 테스트 → 배포 → 운영)를 관리
  • task를 기능·버그·잡무, AI 담당·내 할 일로 나눠 관리
  • GitHub 배포와 Actions 결과를 5분마다 수집하고, 스토어 제출 같은 수동 배포도 기록
  • task·실행·기획·배포가 앱별 히스토리로 쌓이고, 저장소의 문서와 디자인 파일을 탭으로 열람
  • 실행마다 비용을 기록해 앱별·월별로 집계
앱 개요, task 보드, 배포 기록, 비용
F7

규칙 관리

모든 세션이 따라야 할 작업 규칙을 대시보드에서 고치면, 다음 세션부터 바로 적용됩니다.

  • 전역 규칙과 앱별 규칙을 나눠 편집
  • 저장하면 Claude Code 규칙 파일을 원자적으로 다시 써서 새 세션부터 적용
  • "코드를 바꾸기 전에 task부터 갱신", "main에 직접 push 금지" 같은 규칙을 한곳에서 관리
규칙 편집 → 새 세션에 적용
03 / 설계

설계 결정

Claude 세션, 대시보드, 실행기가 서로 다른 입구로 들어오지만 규칙은 한 곳에만 둡니다.

입구는 얇게, 규칙은 한 곳에

hook, MCP, REST, runner는 입구 역할만 하고, 상태 전이와 검증은 도메인 모듈에만 두었습니다. 어느 경로로 들어와도 같은 규칙이 적용됩니다.

Redis 없이 Postgres 하나로

큐, 재시도, 동시 실행 제한, cron을 pg-boss로 처리했습니다. 맥북 한 대에 상주하는 서비스라 움직이는 부품을 줄이는 것이 곧 안정성이었습니다.

실행기를 갈아 끼울 수 있게

지금은 claude CLI를 자식 프로세스로 띄워 stream-json을 파싱합니다. 실행기를 인터페이스 뒤에 두어 Agent SDK로 바꿔도 나머지는 그대로입니다.
