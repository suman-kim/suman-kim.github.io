01 / 왜 만들었나

AI에게 맡기는 건 쉬웠고, 관리하는 건 어려웠습니다

소셜 앱, 구인 앱, 게임 통계 서비스까지 여러 앱을 혼자 Claude Code로 개발하고 있었습니다. 코드는 빠르게 나왔지만, 앱과 저장소가 늘어날수록 같은 문제가 반복됐습니다.

01흩어진 task

task가 저장소마다 Task Master 파일로 따로 있었습니다. 한 앱에만 270개가 쌓였고, 앱을 오가면 전체 진행 상황이 보이지 않았습니다.

02매번 끊기는 맥락

새 세션을 열 때마다 지금 하던 일을 다시 설명해야 했습니다. 한 번 지적한 실수도 다음 세션에는 남지 않아 또 반복됐습니다.

03지켜지지 않는 규칙

"task부터 갱신", "main에 직접 push 금지" 같은 규칙을 파일로 적어 둬도 지침일 뿐이라, 에이전트가 어길 수 있었습니다.

04여기저기 흩어진 상태

어느 세션이 답을 기다리는지는 터미널에서, PR은 GitHub에서, 배포는 Railway에서 따로 봐야 했습니다. 비용은 알 수도 없었습니다.

그래서 세 가지 원칙을 세웠습니다

  1. 01
    기준은 한 곳에

    task, 기획, 실수 기록, 실행, 배포를 하나의 DB에 모았습니다. 저장소에 흩어져 있던 task 파일은 한 번 가져온 뒤 더 이상 쓰지 않습니다.

  2. 02
    지침이 아니라 강제로

    꼭 지켜야 하는 규칙은 문서가 아니라 hook으로 막았습니다. task 없이는 코드를 고칠 수 없고, push와 PR은 에이전트가 아니라 시스템이 합니다.

  3. 03
    사람은 결정만

    실행, 기록, 배포 추적은 시스템이 맡고, 사람은 기획 승인, 질문에 대한 답변, PR 머지만 합니다.

A. 세션이 시작될 때

  1. Claude 세션세션 시작

    터미널이든 백그라운드든 모든 세션이 같은 경로를 탑니다.

  2. hook세션 정보 전달

    작업 폴더와 세션 ID를 관제 서버로 보냅니다.

  3. 관제 서버앱 판별 · task 연결

    작업 폴더로 어느 앱인지 찾고, 이 세션에 연결된 task를 확인합니다.

  4. 관제 서버맥락 블록 조립

    앱 → 이 세션의 task → 열린 task → 실수 기록 순서로, 8,000자 안에서 중요한 것부터 담습니다.

  5. Claude 세션맥락을 알고 시작

    다시 설명하지 않아도 하던 일과 피해야 할 실수를 압니다.

B. 코드를 고치기 직전

  1. Claude 세션수정 · 셸 실행 시도

    파일 수정과 Bash만 검사합니다. 읽기는 언제나 허용합니다.

  2. hook실행 전에 확인 요청

    도구를 실행하기 전에 관제 서버에 통과 여부를 묻습니다.

  3. 관제 서버가드 판정
    통과
    • 진행 중 task가 연결된 세션
    • 시스템이 띄운 세션
    • 관제 서버가 꺼져 있을 때
    차단
    • 진행 중 task 없음
    • 등록되지 않은 프로젝트 폴더
    • 막힌 이유와 푸는 방법을 세션에 안내

C. 도구를 쓴 직후

  1. hook사용 기록 전달

    명령과 도구 사용이 자동으로 쌓입니다. 토큰과 키는 가려서 저장합니다.

  2. 관제 서버task 상태 변경이었나?

    응답이 아니라 DB의 실제 상태를 보고 판단해, 거부된 전이는 무시합니다.

    진행 중 · 답변 대기
    • 세션과 task 연결
    • 수정이 풀림
    리뷰 · 완료
    • 연결 해제
    • 다음 일은 새 task로
  1. 사람task 실행

    대시보드에서 실행을 누르거나 API를 한 번 호출합니다.

  2. 관제 서버실행 대기열에 등록

    pg-boss 큐가 동시에 2개까지 꺼냅니다. 맥북 CPU와 디스크를 지키기 위한 제한입니다.

  3. runner격리된 작업 공간 준비

    task마다 git worktree와 전용 브랜치를 만들고, 앱별 준비 명령(의존성 설치 등)을 실행합니다.

  4. runnerClaude 실행

    task 설명, 기획 명세, 완료 조건을 담아 에이전트를 실행합니다. 앱별로 허용한 도구만 쓰고, push 권한은 없습니다.

  5. 관제 서버로그 저장 · 실시간 전송

    출력 이벤트를 DB에 남기고 WebSocket으로 대시보드에 바로 보여 줍니다. 원본도 그대로 보관합니다.

  6. 관제 서버결과 판정

    에이전트의 마지막 구조화된 출력으로 어떻게 끝났는지 가립니다.

    완료
    • 커밋 확인
    • 사전 검사, 실패하면 PR을 만들지 않음
    • 시스템이 push하고 PR 생성
    • task를 리뷰로
    질문
    • task를 답변 대기로
    • 사람이 대시보드에서 답변
    • 같은 세션으로 이어서 실행 ↺ 4단계
    실패
    • 오류, 사용량 한도, 중지를 구분해 기록
    • 사유를 대시보드에 표시
    • 다시 실행해 완료하면 실패 표시 정리
  7. 사람PR 리뷰 · 머지

    머지는 언제나 사람이 합니다.

  8. GitHub머지 감지

    5분마다 GitHub를 확인해 머지된 PR을 찾습니다.

  9. 관제 서버task 완료 · 정리

    task를 완료로 바꾸고 worktree를 지웁니다. 실행 비용은 앱별·월별로 합산됩니다.

  1. 관제 서버기획 생성 시작

    앱별 주기에 맞춰 자동으로, 또는 즉시 시작합니다. 구독 사용량이 80%를 넘으면 건너뜁니다.

  2. runner읽기 전용 에이전트가 기획 작성

    앱 방향성 메모, 열린 task, 이전 반려 사유를 읽고 정해진 형식으로 기획을 냅니다. 코드는 읽기만 하고, 새 앱 기획은 비슷한 서비스와 시장도 웹에서 조사합니다.

  3. 사람검토
    승인
    • task와 기획 명세 생성
    • 기존 앱이면 task 실행 흐름으로
    수정 요청
    • 요청을 더해 새 버전 작성 ↺ 2단계
    반려
    • 사유를 저장해 다음 기획에 반영
  4. runner새 앱이면: 프로젝트 만들기

    폴더를 만들고 git을 시작한 뒤, README와 기획 문서로 첫 커밋을 합니다.

  5. GitHub비공개 저장소 생성

    같은 이름의 저장소가 있으면 덮어쓰지 않고 멈춥니다.

  6. 관제 서버작업 폴더 신뢰 등록

    방금 만든 폴더만 Claude Code 신뢰 목록에 올려, 백그라운드 세션이 시작될 수 있게 합니다.

  7. Claude 세션백그라운드 세션 시작

    기획 읽기 → UI 시안 → 첫 task 구현 → PR 순서로 진행합니다. 원격으로 이어 볼 수 있습니다.

  8. 관제 서버실패하면 이어서 재시도

    끝난 단계는 건너뛰고 실패한 단계부터 다시 합니다. 세션을 못 띄우면 runner가 첫 task를 대신 실행합니다.

03 / 기능

기능과 시연

각 기능이 어떤 문제를 풀었는지와 실제로 동작하는 모습을 함께 담았습니다.

맥락 주입task 가드task → PR 기획 승인새 앱 시작대시보드규칙 관리
F1

세션 맥락 주입과 실수 학습

세션을 열 때마다 하던 설명을 시스템이 대신합니다. 지적받은 실수는 다음 세션부터 바로 반영됩니다.

  • 세션이 시작되면 hook이 현재 앱, 이 세션의 task, 열린 task, 이 앱의 실수 기록을 맥락 블록으로 주입
  • 세션은 MCP 도구로 task 상태 변경, 실수 기록, 기획 명세·인수인계 문서 저장, 버그 등록을 직접 수행
  • 명령과 도구 사용, 종료가 자동으로 기록되고 비밀값은 가려서 저장
  • 맥락 블록은 8,000자 상한 안에서 우선순위대로 구성
새 세션에 맥락 블록이 들어가는 모습
F2

task 강제 가드

규칙 문서에 적어 두는 것만으로는 지켜지지 않아서, task 없이는 코드를 고칠 수 없게 시스템으로 막았습니다.

  • 직접 연 세션은 진행 중 task가 연결되기 전까지 파일 수정과 셸 실행을 차단, 읽기는 허용
  • 세션이 task를 doing으로 바꾸는 순간을 감지해 세션과 task를 자동 연결, review로 넘기면 해제
  • 등록되지 않은 프로젝트 폴더도 차단해 관리 밖의 작업을 방지
  • 관제 시스템이 꺼져 있으면 가드도 열어, 관리 도구 때문에 개발이 멈추지 않도록 설계
task 없이 수정 시도 → 차단 → task 연결 후 진행
F3

task 하나로 PR까지 자동 실행

task를 실행하면 격리된 작업 공간에서 에이전트가 일하고, 검사를 통과한 결과만 PR로 올라옵니다.

  • task마다 git worktree와 전용 브랜치를 만들어 원본 저장소와 격리
  • 에이전트 실행 로그를 WebSocket으로 대시보드에 실시간 전송
  • 에이전트에게 push 권한을 주지 않고, 사전 검사를 통과하면 시스템이 직접 push하고 PR 생성
  • 에이전트가 질문으로 끝나면 대기, 답하면 같은 세션으로 이어서 실행
  • 동시 실행 수와 허용 도구를 설정으로 제한, PR이 머지되면 task 자동 완료
실행 → 실시간 로그 → 질문에 답변 → PR 생성
F4

기획 생성과 승인

앱마다 다음에 할 일을 제안받고, 사람은 승인·수정·반려만 결정합니다.

  • 앱의 방향성 메모, 열린 task, 최근 기획과 반려 사유를 입력으로 기획을 생성
  • 기획 단계의 에이전트는 읽기 도구만 사용
  • 승인하면 예상 task와 기획 명세가 자동으로 만들어지고, 수정 요청은 새 버전으로 이어짐
  • 앱별 주기를 정해 자동 생성할 수 있고, 사용량이 높으면 건너뜀
기획 생성 → 검토 → 승인 → task 생성
F5

새 앱 기획에서 첫 PR까지

저장소도 없는 새 앱을 구상하고, 승인하면 프로젝트 시작부터 첫 구현까지 이어집니다.

  • 기존 앱의 스택을 참고하고 비슷한 서비스와 시장을 웹에서 조사해 새 앱 기획을 제안
  • 승인하면 폴더 생성과 초기 문서 커밋, GitHub private 저장소 생성
  • 백그라운드 Claude 세션이 기획을 읽고 첫 task를 구현해 PR까지 진행
  • 중간에 실패하면 끝난 단계는 건너뛰고 이어서 재시도
새 앱 기획 승인 → 저장소 생성 → 첫 PR
F6

통합 대시보드

여러 앱의 상태와 할 일, 배포, 히스토리를 한 화면에서 봅니다.

  • 앱마다 진행 상태를 색으로 표시하고, 개발 단계(기획 → 설계 → 개발 → 테스트 → 배포 → 운영)를 관리
  • task를 기능·버그·잡무, AI 담당·내 할 일로 나눠 관리
  • GitHub 배포와 Actions 결과를 5분마다 수집하고, 스토어 제출 같은 수동 배포도 기록
  • task·실행·기획·배포가 앱별 히스토리로 쌓이고, 저장소의 문서와 디자인 파일을 탭으로 열람
  • 실행마다 비용을 기록해 앱별·월별로 집계

04 / 설계

설계 결정

Claude 세션, 대시보드, 실행기가 서로 다른 입구로 들어오지만 규칙은 한 곳에만 둡니다.

입구는 얇게, 규칙은 한 곳에

hook, MCP, REST, runner는 입구 역할만 하고, 상태 전이와 검증은 도메인 모듈에만 두었습니다. 어느 경로로 들어와도 같은 규칙이 적용됩니다.

Redis 없이 Postgres 하나로

큐, 재시도, 동시 실행 제한, cron을 pg-boss로 처리했습니다. 맥북 한 대에 상주하는 서비스라 움직이는 부품을 줄이는 것이 곧 안정성이었습니다.

실행기를 갈아 끼울 수 있게

지금은 claude CLI를 자식 프로세스로 띄워 stream-json을 파싱합니다. 실행기를 인터페이스 뒤에 두어 Agent SDK로 바꿔도 나머지는 그대로입니다.

매일 쓰는 서비스로 운영

개발 도구라도 매일 의존하는 서비스라서, 꺼지거나 데이터를 잃지 않는 것을 기능만큼 중요하게 다뤘습니다.
